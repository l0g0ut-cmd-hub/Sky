НЕБЕСНЫЙ ПРИЛИВ (Sky Tide) — журнал разработки и передача дел
================================================================
Обновлено: 10.11.2026, после сборки 30. Писал Claude (Anthropic) для продолжения работы в другом ассистенте.

1. ЧТО ЭТО
----------
Прототип dark-fantasy игры: воздушные корабли над морем закатных облаков. Цель прототипа — «просто корабль
в небе, джойстик и вращение камеры», но качество — «ААА»: главное красота и зрелищность.
Платформа: Android (телефон пользователя, тест на устройстве). Движок: Unity 6000.0.36f1.

------------------------

3. СБОРКА (CI) — ВАЖНО ПРО ЛИМИТ
--------------------------------
!!! ЛОКАЛЬНЫЙ UNITY НЕ НУЖЕН И ЕГО НЕТ. Unity Editor запускается ТОЛЬКО в GitHub Actions (контейнер GameCI).
    Работа так: правишь код/шейдеры в репозитории → коммит в main → по команде владельца пуш в apk-build →
    CI сам собирает сцену (SceneBuilder), снимает кадры (SceneShots) и собирает APK. Ошибки компиляции C#
    и шейдеров — в logs/run-N.log ветки ci-logs (искать "error CS", "Shader error", "Exception").
    Результат смотреть по кадрам shots/*.jpg в ветке apk-latest, на телефоне — APK оттуда же.
    Python-инструменты (tools/) работают без Unity: numpy, Pillow, opencv.

- Workflow: .github/workflows/build-android.yml (GameCI CLI v0.1.72, Unity 6000.0.36f1, Android IL2CPP ARM64).
- Сборка запускается ТОЛЬКО пушем в ветку apk-build (или вручную workflow_dispatch). Пуш в main сборку НЕ запускает.
    git push -f origin main:apk-build
- ПРАВИЛО ВЛАДЕЛЬЦА: не собирать на каждую правку. Копить изменения в main и собирать пакетом, когда владелец
  скажет «собирай». Одна сборка ~20–30 мин (из них ~1.5 мин — запекание импосторов в CI на CPU).
- Результаты:
    ветка apk-latest — APK + папка shots/ (кадры, снятые в редакторе CI: 01–08 рисованный режим, 30–37 объёмный,
      40–43 залпы, 90–93 отладка, 93_dbg_impostors — лист снимков облаков) + info.txt (номер запуска и sha);
    ветка ci-logs — logs/run-N.log (лог без секретов);
    артефакты запуска: SkyTide-Android-APK, SkyTide-Shots.
- Номер сборки = номер запуска GitHub (GITHUB_RUN_NUMBER), пишется в Assets/_Project/Resources/BuildNumber.txt
  и показывается в игре внизу справа («Сборка N»).
- Проверка «MonoBehaviour в файле с другим именем» — CI падает, если имя класса MonoBehaviour ≠ имени файла.

5. КАК УСТРОЕНЫ ОБЛАКА (объёмный режим, по умолчанию с 30-й сборки)
--------------------------------------------------------------------
- Героические башни (7 шт, радиус 150–250 м, 480–1700 м от камеры): форма — 3 шаблона из 28 сфер (мягкое
  объединение), запечены в 3D-текстуру 40×72×120 RGBA: R — поле формы, G — оптическая толщина к солнцу,
  B — видимость неба (свет запечён, башни не вращаются). Поверхность лепит 3D-шум. Марш 40 шагов в 1/4
  разрешения, шаги растут с расстоянием, упорядоченный сдвиг (Байер 4×4) + двойное размытие, сведение
  с учётом глубины. Габарит башни — коробка поля (раньше шар срезал облако → «полупрозрачная сфера»).
- Море облаков (с 28-й): объёмный слой y −60…20 м, покрытие — 2D-«погода», верх бугрится 3D-шумом, свет —
  два шага к солнцу, яркость солнца ×0.26 (против пересвета). Считается до первой встречи с башней.
- Облако расступается узким коридором камера→корабль (ClearFactor), чтобы не закрывать корабль.
- Импосторы: 3 варианта башен × 16 азимутов по 256² снимаются тем же шейдером при первом включении
  объёмного режима (заминка 1–2 с на телефоне), сглаживаются. Поле: 12 больших + 26 малых облаков до 3.2 км,
  растут из моря облаков, наклоняются к камере, гаснут при крутом взгляде и вблизи.
- Рисованный режим (кнопка «Облака: …»): спрайты из атласа, плоские; при взгляде сверху растворяются.

8. ЗАМЕЧАНИЯ ВЛАДЕЛЬЦА, КОТОРЫЕ НАДО ДЕРЖАТЬ В ГОЛОВЕ
-----------------------------------------------------
- Плоские облака недопустимы — всё должно выглядеть объёмным, особенно под кораблём.
- Без «кучек»: приплюснутые варианты башен выглядели плохо — убраны.
- Пересвет моря облаков; корабль не должен тонуть в белом.
- Ничего «грязного»: зерно, полосы, круглые дыры/сферы в облаках сразу видны.
- Сборки — пакетом, по команде.

10. ЗАДАЧА 2 ДЛЯ ПРОДОЛЖЕНИЯ: «ядро падает в море облаков» + «вспышки подсвечивают облака»
-----------------------------------------------------------------------------------------
Цель (зрелищность, ААА): залп должен «жить» в облаках. Ядро, ушедшее в море облаков, выбивает клуб облачной
пены; вспышки дул и взрывы на мгновение тепло подсвечивают ближайшие облака, дым и корпус.

ЧТО УЖЕ СДЕЛАНО (примитивная база, сборка 31):
 a) FxSystem.CloudSplash(Vector3 at) — 7 розоватых клубов дыма (Kind.Smoke), растут 4→17 м, поднимаются.
    Вызывается, когда ядро опускается ниже deckTop − 15 м (в FxSystem.Simulate, ветка Kind.Ball; очередь splashes).
 b) Глобал шейдера _SkyTideFlash (xyz позиция, w сила), объявлен в Shaders/SkyTide.cginc, функция
    SkyTideFlashLight(p) — тёплый свет, спадает как 1/(1 + d²/2000). Добавлен в источник света:
    море облаков — Deck() в VolumetricClouds.shader; башни — fragMarch (кроме режима bake).
    FxSystem.Flash(at, power): выстрел — 2.5, взрыв — 4×scale; гаснет exp(−14·t). Хранится ОДНА вспышка (самая сильная).

11. ИЗУЧЕНО: КАК УБРАТЬ МЫЛО (план для следующего шага, по VolumeCloud для Built-in RP — тот же конвейер, что у нас)
-------------------------------------------------------------------------------------------------
Источник: https://gitee.com/eloncode/VolumeCloud (Unity, Standard/Built-in RP). Их путь: отказались от узора 4×4
(у нас сейчас Байер 4×4 + 3 размытия = мыло), перешли на марш с МАЛЫМ числом шагов + временное перепроецирование
(TAA облаков, по Playdead «Temporal Reprojection AA in INSIDE», GDC 2016). «Оценка глубины облака» убрала размытие
при повороте камеры. «Hi-Height map» — 2D-карта пропуска пустоты (для взгляда сверху на слой — наш случай).
Цифры (GTX 1060): половина разрешения ~1 мс; над слоем облаков дороже (5 мс) — там и нужен пропуск пустоты.

План внедрения у нас (VolumetricClouds.cs / .shader):
 1. История: два RenderTexture ARGBHalf (1/4 разрешения, ping-pong), хранить cloud rgba + в отдельном R16 — средняя
    дистанция облака meanDist (уже считается в fragMarch/Deck; вывести её, напр. во 2-й RT или упаковать).
 2. Каждый кадр сдвиг шагов — другой: jit = frac(Bayer4(px) + кадр*0.618) (или 16 фаз Байера по кадрам) —
    узор меняется во времени, накопление его усредняет; размытие оставить ОДНО или убрать.
 3. Перепроецирование: мировая точка = ro + rd*meanDist (для неба/пустоты — далёкая точка 1e4 по rd);
    prevUV = prevViewProj * точка; если prevUV в [0,1] — history = tex(prev, prevUV).
 4. Ограничение истории (против призраков): min/max соседей 3×3 текущего кадра в низком разрешении, clamp history.
 5. Смешивание: result = lerp(current, clampedHistory, 0.9); при сильном движении/выходе за экран — 0.5 или 0.
 6. Апскейл до полного экрана — как сейчас (fragComposite с глубиной), но уже из накопленного буфера → можно
    вернуть меньше шагов (40 → 24–28) и получить FPS, а чёткость — за счёт накопления.
 7. Hi-Height (опционально): 2D-текстура верха моря облаков (топ topH по «погоде»), шаг сразу до верха слоя.
 Проверка: в CI кадры статичны — TAA там не проявится; смотреть на телефоне (мыло при движении, призраки за кораблём).

(сделано, сборка 39) Пункты 1–6 раздела 11 в упрощённом виде: история 1/4 разрешения, перепроецирование по плоскости
   верха моря облаков (лучи вниз) / 1500 м (вверх), зажим 3×3, вес 0.88, сдвиг шагов меняется по кадрам,
   одно размытие. Если на телефоне «призраки» при резком повороте — снизить temporalBlend до 0.8.

Что взять (по убыванию пользы):
 A. Меньше шагов за счёт накопления (сборка 39 уже копит кадры): башни steps 40 → 24–28, море облаков
    deckSteps 18 → 12. Прямой прирост FPS. Делать только если в 39 нет призраков.
 B. Hi-Height map — пропуск пустоты над слоем: 2D-текстура (напр. 256², обновлять при сдвиге «погоды» или
    считать раз и смещать UV ветром) с высотой верха моря облаков topH (формула из DeckDensity без детализации,
    с запасом +10 м). В Deck(): t0 = вход луча в плоскость max(topH-карта) по ходу луча — грубо: шагать по карте
    крупно (8–12 выборок 2D) до точки, где y луча < карта, затем обычный марш. У VolumeCloud самая дорогая сцена —
    именно взгляд сверху на слой (наш случай).
 C. Настоящая глубина облака для перепроецирования: сейчас в fragTemporal — плоскость верха моря / 1500 м.
    Если в 39 при поворотах мылит/двоит — выводить meanDist из fragMarch (второй RT RHalf или упаковка) и
    перепроецировать по ней.
 D. Если призраки при резком повороте: temporalBlend 0.88 → 0.8; или сбрасывать вес при большом угле поворота
    камеры за кадр (сравнить forward прошлого и текущего кадра).
 E. Шумоподобный сдвиг по кадрам: сейчас frac(Bayer4 + кадр·0.618); у VolumeCloud узор 4×4 заменён на полный
    экран + перепроецирование — можно перейти на blue noise (текстура 64², сдвиг по кадрам).
